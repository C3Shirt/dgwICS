# 通用验收合同与工具能力边界

## 原则

不为每个工程新增 `sc001_validator`、`weight_sorting_validator` 等专用验收函数。
需求决定规则，软件接口决定适配器，测量方式决定可复用原语。
本次临时加入的 `single_conveyor` 验收器已撤回，当前默认使用 `signal_contract`。
旧重量解码器保留兼容用途，不作为新场景的默认生成路径。

```mermaid
flowchart LR
    R[自然语言需求] --> P[Planner: 工艺与执行合同]
    P --> S[模型生成信号表]
    S --> A[模型生成操作计划]
    A --> C[模型生成检查规则]
    C --> V[工具校验并冻结合同]
    V --> G[Scene Agent / 场景工具]
    G --> L[PLC Agent / 编译下载]
    L --> T[通用采样与原生操作执行器]
    T --> E[同一个规则解释器]
    E --> M[视觉与过程证据审查]
    M --> F[按证据路由修复]
```

## 可复用原语

| 原语 | 固定能力 | 模型填写的场景参数 |
|---|---|---|
| `sequence` | 统计有测量来源的边沿顺序 | 信号、升降沿、次数、关联工艺步骤 |
| `duration` | 用采样区间界定真实持续时间 | 开始/结束边沿、时间上下限、保持条件 |
| `alternation` | 检查前一操作完成前是否有新的开始 | 开始/完成信号、次数 |
| `invariant` | 检查条件成立时的信号约束 | 条件与期望，BOOL 或原始数值比较 |
| `probe_state` | 检查原生操作保持窗口内的实际响应 | 操作阶段、稳定等待、输入与输出条件 |

工具不包含具体场景名、固定分拣阈值、两秒计时常量或某个 PLC 状态机。
两个不同场景可使用同一个 `duration` 检查不同信号和时长；新场景无需新增该函数。
如果现有原语不能表达所需测量，扩展测量能力，而不是按工程编号增加分支。

## 模型与工具的责任

Planner 当前分五个有独立记录的子任务：需求规格、执行合同、测量信号、操作计划、检查规则。
信号表固定后，后两个子任务必须使用同一命名空间。工具校验枚举、引用、时间范围、操作释放、
操作与检查的覆盖关系，然后拼装完整任务。没有人工改写模型候选。
`training-data/derived/task-assembly.json` 保留五个原始候选 ID 与哈希，可重放检查。

信号以 object ID、方向和 tag index 声明；工具通过当前 I/O 合同解析实际 GUID。
输入极性来自已验证的原生语义，不接受模型凭常识推测。数值比较默认是原始值，不能冒充已校准质量。
缺少观测、强制输入、故障状态不明、时长区间过宽、没有动作回执或检查没有适用样本，均不能通过。
同一采样帧内的边沿不声称具有严格的帧内先后顺序；时长结果保留上下界与原始样本引用。

模型可以制定受限的原生按钮操作计划；当前执行能力仅覆盖 Start、Stop、Reset momentary buttons。
每次按下/释放都有原生回执和真实 Tag 样本，失败时释放仍按下的按钮，并保留部分证据。
每个动作阶段需要同时测量按钮状态和相关 PLC 输出，不能只把工具调用成功当作过程完成。

已验证的 PLC I/O 容量先交给规划器；当前工程有 14 个 BOOL 输入、12 个 BOOL 输出端点，
其中规划预算保留一个系统 Running 输入。超容量设计在规划阶段拒绝，不虚构额外 PLC 地址。
软件适配器在 PLC 下载前断开 Factory I/O 驱动，下载后检查实际 I/O 连接持续稳定再开始运行。
这是协议生命周期能力，与工业场景的类型无关。

## 仍需补齐的通用性

可执行合同语法正确，并不能证明它完整覆盖用户需求。后续需要独立的需求覆盖与合同语义审查，
避免遗漏条件或把不充分的检测信号当作完成标准。应在 PLC 生成前冻结标准，并以真实证据解释失败。
视觉模型也不能用“验收未过”倒推出一个没有证据的 PLC 或几何故障。

当前布局求解仍只验证了一个滚筒输送机及其周边部件的相对关系；不能外推为全部 100 场景已支持。
更广泛布局需要基于组件几何、连接端口与约束图扩展求解器。数值原始范围已能检查，质量单位转换、
并发物料身份、复杂模拟量标定等仍需对应的测量能力和独立验证。
