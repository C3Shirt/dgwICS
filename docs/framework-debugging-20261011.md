# 分阶段模型与工具边界

本轮遵循用户要求：流程设计、部件选择和 PLC 状态机须来自实际框架的模型调用；坐标算术、I/O 与已测极性变换来自有凭证的工具；观察者只修框架，
不手改模型方案、ST、视觉反馈或运行证据。每次框架修改后新建运行目录，运行中冻结源码。

```mermaid
flowchart LR
  A[需求] --> B[Agent1 对象与流程]
  B --> C[Agent1 执行合同]
  C --> D[Agent1 验收要求]
  D --> E[工具校验与组合]
  E --> F[Agent2 部件选择与相对关系]
  F --> FT[原生几何工具计算坐标]
  FT --> G[Agent2 部件配置]
  G --> H[模板校验 供料约束 I/O分配]
  H --> I[原生加载 坐标边界 三视图]
  I --> J[Agent3 当前证据审核]
  J -->|几何问题| F
  J -->|通过| K[PLC Agent 控制代码]
  K --> KT[工具 I/O声明 输入极性归一化]
  KT --> L[编译 绑定 下载 连接]
  L --> M[运行采样 独立验收]
  M --> J
```

## 已实施

- 文字角色切换到服务实际支持的 `deepseek-v4-pro`；视觉仍使用 Aliyun 配置中的模型。
- 规划模型只看部件能力摘要，布局模型只看任务所需模板，配置模型只看已选模板。
- 规划拆成三个有独立 schema 的模型子任务，工具记录组合来源；布局和配置拆成两个子任务。
- 配置属性先验证具体模板的节点与属性。配置类问题保留布局，只重试配置；几何问题重新规划。
- 单件供料工具执行已验证的任务合同：UpTo=1、PLC 部件输出解除模板强制值，并保留变更回执。
- I/O 工具分配低位连续 BOOL 通道，基于 GUID 关联设备；原生内存地址另行去重，避免克隆信号共用。
- 原生桥接记录实际对象边界、状态、已关闭的旧加载失败弹窗；相机按原生边界拍摄三视图。
- 上游交接元数据从下游输入视图移除；原始文件与版本仍先行验证，当前交接 ID 不允许混用。
- 视觉配置使用非思考请求及动态 JSON Schema；schema 限定当前角色、流程、证据与版本标识，
  不提供审核结论，也不把假设变成已证实原因。服务能力依据
  [Aliyun 官方结构化输出说明](https://www.alibabacloud.com/help/zh/model-studio/qwen-structured-output)。
- 所有原始候选与修复保存为待审核数据，未自动升级为 SFT/DPO 正样本。

## 实验边界与观察

`observer-sc001-20261010-006`：旧 Flash 流程已加载场景，但视觉服务返回空数组，未通过审核。

因此映射错误由确定性工具消除，不把换模型本身宣称为修复。
`009`：单件检查发现继承的强制输出，模型又使用错误的 Emitter 属性路径；其后加入约束工具。
`010`：模型反复使用上游交接 ID；其后增加输入视图的元数据投影。
`012`：验收规则被返回为单个对象；增加不改语义的对象到数组适配，并保留格式转换记录。
`013`、`014`：已通过规划、场景生成、BOOL 绑定、原生加载及三视图截图；视觉识别出部件
衔接问题，但反馈角色、schema 或流程 ID 不满足合同。其后加入服务端 JSON Schema 约束。

具体次数、模型、耗时、来源、反馈及最终状态以每个 `runs/observer-sc001-*/` 内的记录为准。
这些记录证明对应阶段发生过，不证明当前场景能够正确供料、停留、排出或停止/复位。

目前运行事件解码器仍以重量试验为专用实现；输送停留流程还需操作者动作工具的联机验证、
事件解码和时长检查。不能仅依据图片、编译或 PLC Run 宣称完整流程通过。
Windows Runtime 服务启动权限与场景/模型问题分别记录，不能通过调整 PLC 逻辑规避权限问题。

## 后续工具化修复

`015`：视觉服务首次按动态 JSON Schema 返回通过，四个角色均收到真实回复；PLC 把工具绑定到 SceneIO，却另建未绑定的局部 I/O，声明检查拒绝。该场景的原生空间数据与截图还显示供料器分离，因此视觉通过不能作为物理连接依据。

`016`：增加工具生成 PLC GVL 和绑定，模型仅返回内部声明与控制逻辑。视觉触发四轮布局修复，但存在坐标轴和长度轴误读，最终达到修复上限，未进入 PLC 阶段。

现增加原生 prefab_geometry 只读查询，返回网格比例（0.125 m）、Y 垂直轴、97 种部件的本地体素边界，以及实际供料原点、输送方向、传感器射线。单输送机布局先检查供料原点位于 XZ 投影内、有限传感器射线可达；加载后使用真实实例尺寸和量程复检。它不改模型坐标，也不证明碰撞、运输、停留时间或整体验收。该工具在回归检查中成功拒绝了 `015` 的分离布局。

原生加载记录按钮的常开/常闭状态；仅对已确认的瞬时按钮增加带凭证的输入极性。PLC 工具拒绝断开的局部别名、未赋值执行器、物理输入写入，并保留原始模型逻辑和工具组合回执。审核能重放组合并检测手改程序。

当前测试：247 项通过。`017` 使用同一需求重新执行，最终结果以该运行的 result.json 为准。Windows Runtime 启动权限仍独立于这些模型/空间检查。

`017`：原生几何工具先拦截错误布局，Pro 仍无法从绝对坐标反馈稳定修好。因而新增相对关系到整数坐标的确定性计算：模型选择模板、主输送机锚点、沿流程的位置比例和传感器侧面；工具计算供料高度、射线朝向、有限量程及卸料体积的出口位置。配置模型再使用已解算布局，不手改场景文件。

`018`：相对布局加载成功，PLC 工具组合通过真实 CODESYS 编译、设备绑定和周期任务检查；模型否定了原生测量的常闭 Stop 极性，并保留实际/臆测的 unresolved，因此部署被阻止。卸料器原生注册失败也提示仍有重叠；其后增加注册检查及 remover_after_conveyor 放置规则。

新增 BOOL 输入归一化仅接受带凭证的实际极性：SceneInputs 为只读副本，TRUE 表示按下/占用/仿真运行。工具在每扫描周期的前导代码计算这些副本；模型只写状态机及输出，不可改写物理输入或重新解释原始极性。原始模型代码、前导转换和完整组合的哈希均可重放。未确认极性会继续阻止生成，未满足的需求不会被工具删除。

当前测试：255 项通过。`019` 使用这些更新重新跑同一需求。编译、绑定和 MainTask 成功仍不等于下载、运行、时间与物料流验收成功。

`019`：四个角色均有真实服务回复；模型选择相对布局、工具解算坐标，场景全部原生注册成功并通过连接与视觉审核。PLC 逻辑在归一化输入接口下经引用反馈修复，unresolved 为空；真实 CODESYS 编译 0 错误 0 警告、设备绑定和周期任务通过。在线扫描报“没有设备及时响应扫描请求”，当前 Runtime 服务为 Stopped，部署/启动未完成。result.json 中 manual_override_detected=false、framework_changed_during_run=[]，工具组合可由模型候选和绑定数据重放。此结果不是完整仿真通过。

其后接入 operator_startup：仿真 Run 后，以当前场景对象 Key 唯一定位 Reset/Start 瞬时按钮，通过原生按钮按下/释放，并保留每次实际标签采样；异常也尝试释放按钮。当前 258 项测试通过。这段运行接入仅通过隔离检查，尚未在本轮联机验证；输送场景事件解码、2 秒时间测量和完整启停复位验证仍待实现/验收。Windows 管理员启动请求未确认服务运行成功，不能以 IDE 已打开代替 Runtime 状态。
# 通用性修正与第 20–26 轮

用户指出按场景增加验收工具会削弱框架通用性后，撤回临时的单输送验收器，改为模型生成
signal_contract 与固定测量原语。Planner 分五个有独立候选记录的子任务；信号表/操作计划先固定，
再生成检查规则。加入规划 I/O 容量预检、操作检查覆盖与下载前驱动断开/连接稳定性检查。
详情与各轮证据边界见 [通用验收设计](generic-acceptance-design.md)。最新测试 272 项通过；
第 24 轮通用合同、软件加载和编译下载/连接通过，但运行采样受原生断连通知阻挡；
第 26 轮在规划容量检查拒绝超额设计。不能把任何一轮标为完整成功。
